# 系统设计一：流式对话系统（STAR）

## Situation

内部知识问答的核心交互是多轮流式对话：用户提问后需要秒级看到逐字输出，能随时停止，断线/超时要有明确失败态，且模型密钥不能暴露给前端。

## Task

设计一个支撑 200 名内部员工同时在线的对话服务：SSE 流式输出、停止生成、失败可重试、按用户计量计费。

## Action

**数据流**：前端 `POST /api/chat/stream`（JWT）→ 后端校验会话归属与配额 → 用户消息落库 → RAG 召回 → 调用 DeepSeek（stream）→ SSE 逐帧下发 → 流末 usage 落库并累计配额。

**关键决策**：

1. **SSE 而非 WebSocket**：单向推送足够，HTTP 友好（复用鉴权中间件、nginx 代理、重试语义）；前端用 `fetch + ReadableStream` 而非 EventSource，因为要带 Authorization 头与 AbortController。
2. **密钥隔离**：DeepSeek 调用只在服务端，前端零密钥；降级路径（超时/5xx）统一转成 SSE `error` 事件，前端渲染失败卡片而非裸断流。
3. **流与事务解耦**：流期间不写库，assistant 消息在流结束时一次 UPDATE；断连（`is_disconnected`）标记 `aborted`，避免半消息悬挂。
4. **背压与心跳**：sse-starlette `ping=15` 防代理断连；nginx `proxy_buffering off`。

**容量估算**：200 并发流 ≈ 200 条 SSE 长连接，FastAPI 单进程异步可承载（每条连接主要是等待模型帧）；瓶颈在 DeepSeek 的并发与 TPM 限额，必要时排队而非扩容应用层。

## Result

首 token 延迟 ≈ 模型首帧延迟（<2s 常规），停止生成即时生效；失败态覆盖超时/5xx/配额/断连四类；本月 token 用量实时可见。

## 四问

- **数据**：sessions/messages 两表，消息含 status（complete/streaming/failed/aborted/pending_confirm）、citations、usage、trace_id；历史取最近 20 条拼上下文。
- **失败**：模型 60s 超时 → TIMEOUT 事件 + failed；5xx 重试一次 → MODEL_ERROR；客户端中断 → aborted；配额耗尽 → QUOTA_EXCEEDED。
- **费用**：流末 `usage`（prompt/completion tokens）按 ¥2/M + ¥8/M 折算，按月累计 quotas 表。
- **评测**：对话正确性由 RAG 评测集覆盖（见 02）；流式体验指标为首 token 延迟与中断恢复率，由 eval 脚本记录 latency_s。
