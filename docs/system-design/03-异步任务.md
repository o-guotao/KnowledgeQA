# 系统设计三：异步任务执行（STAR）

## Situation

文档切分与向量化是秒级到分钟级的重活，不能在 HTTP 请求内完成；同时需要可观测的失败处理：超时、重试、死信，且多实例下不能重复执行。

## Task

设计不引入 Celery/Redis 的轻量任务系统：以 Postgres tasks 表为队列，支持抢占、超时、指数退避重试、死信与全链路 traceId。

## Action

**模型**：tasks 表含 type/payload/status/retry_count/max_retries/next_run_at/started_at/finished_at/duration_ms/error/trace_id。状态机 `pending → running → done / failed → dead`。

**抢占**：
```sql
UPDATE tasks SET status='running', started_at=now()
WHERE id = (SELECT id FROM tasks WHERE status IN ('pending','failed')
            AND next_run_at <= now() ORDER BY next_run_at
            FOR UPDATE SKIP LOCKED LIMIT 1)
RETURNING id;
```
`FOR UPDATE SKIP LOCKED` 保证多 worker 不重复领取；单条 UPDATE 原子完成「领取+标记」，无竞态窗口。

**执行与超时**：`asyncio.wait_for(run_task, TASK_TIMEOUT_SECONDS)` 软超时；超时/异常进失败处理：`retry_count+1`，`next_run_at = now + base*2^(n-1)`（5s→10s→20s）；超过 max_retries 置 `dead`，不再被消费，留待人工审计。

**traceId**：任务入队时取生产请求的 traceId（如文档上传请求），worker 执行日志全程同一值，与 API/SSE/费用记录可串联。

**关键决策**：

1. **表队列而非消息队列**：任务量小（每分钟个位数），Postgres 已存在；换来的是零新增组件、事务一致（入队与文档记录同库）、死信即一行状态。
2. **dead 而非丢弃**：死信可查询、可审计、可人工重置重放；删除文档的级联不影响任务记录（user_id SET NULL）。
3. **幂等执行**：`ingest_document` 先 `DELETE FROM chunks WHERE document_id=?` 再批量插入，重试/重放结果一致。

## Result

`demo_fail` 恒超时任务可复现完整链路：running → failed×3（退避 5/10/20s）→ dead（证据见 docs/evidence/deadletter-死信演示.md）；正常 ingest 任务 duration_ms 落库可分析。

## 四问

- **数据**：tasks 表即队列与审计日志；payload JSON 只放引用（document_id），不放正文。
- **失败**：超时与异常统一进退避重试，超限死信；文档状态联动标记 failed；worker 崩溃后任务停留在 running——以 started_at 超阈值巡检回收（可改进点）。
- **费用**：任务本身零外部调用费（embedding 本地）；问答侧费用见 01。
- **评测**：以 demo_fail 演示验证状态机；以 ingest 任务的 duration_ms 与成功率作为处理链路健康指标。
