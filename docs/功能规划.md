## 一、现状盘点

### 已实现（对照完整 Agent 的核心能力）

| 能力域 | 现状 | 代码位置 |

| 多页前端 | 登录/对话/文档管理/模型设置 四页 | `pages/` |

### 关键缺陷（当前代码，必须正视）

1. **embedding 在本地环境不可用**：`fastembed` 依赖 `onnxruntime`，其在 Python 3.14 下 DLL 加载失败。当前 `embedding.py` 无降级方案，本地（非 Docker/Python 3.12）跑 worker 处理文档必然失败。Docker（Python 3.12）正常。
2. **召回是单一向量 top_k**：无重排序、无关键词混合、无元数据过滤。文档量稍大（>50 篇、>5000 chunk）后精度明显下降。
3. **文档管理是平面列表**：无文件夹/标签/权限分组，无批量操作，无版本管理。
4. **SQLite 兼容改造已回滚**：`storage_compat.py` 不存在，`config.py` 无 `db_backend`，本地无 Docker 演示路径已断裂。

## 二、功能缺口（对比完整内部问答 Agent）

按"完整内部知识问答 Agent 应具备什么"对标，缺口分四档：

### P0｜阻塞生产可用的缺口

| 缺口 | 为什么阻塞 | 方向 |
| --- | --- | --- |
| **embedding 环境鲁棒性** | onnxruntime 在非 3.12 环境崩溃，无 fallback，文档无法入库 | embedding 服务抽象化：fastembed（Docker）/ OpenAI embedding API / 本地 sentence-transformers 三选一，按配置切换 |
| **召回质量基线** | 单一向量 top_k=5，精度无保障，评测指标无法稳定复现 | 混合检索 + 重排序（见第四节） |
| **数据备份与恢复** | Postgres/SQLite 与对象存储无备份策略，误删/损坏即丢数据 | 定时 pg_dump + 对象存储快照 + 恢复演练文档 |
| **HTTPS 与域名** | 生产对外必须 HTTPS，当前仅 localhost/HTTP | nginx 反代 + Let's Encrypt（`deploy-vm.md` 已有草稿，需落地） |

### P1｜显著影响体验的缺口

| 缺口 | 影响 | 方向 |
| --- | --- | --- |
| **重排序（rerank）** | 向量召回 top_k 后直接进 prompt，相关性排序粗糙 | 召回 top 20 → BGE-reranker 重排 → top 5 |
| **混合检索** | 纯向量召回对专有名词/编号（如"METRIC-0012"、"91330100MA27XT2K8B"）召回弱 | 向量 + PostgreSQL `tsvector` 全文检索（BM25 近似）融合 |
| **文档分类与权限分组** | 全部文档平铺，多部门共用时分不清归属 | 文件夹/标签 + 按部门/角色的文档可见性 |
| **批量上传与管理** | 只能单文件上传，几十篇文档操作繁琐 | 多选上传、批量删除、批量重新切分 |
| **答案质量反馈** | 无用户对答案的评分（点赞/点踩），无法发现坏答案 | 消息级 feedback 字段 + 管理端看板 |
| **可观测性后端** | 日志是 JSON 但无查询界面，Langfuse/追踪 UI 未接 | 接 Langfuse（计划资料已提及）或自建简单追踪查询页 |

### P2｜扩展能力的缺口

| 缺口 | 方向 |
| --- | --- |
| **多模态文档** | 图片 OCR（PaddleOCR/Tesseract）、表格提取（pdfplumber/camelot）、Word/PPT/Excel（python-docx/python-pptx/openpyxl） |
| **增量更新与失效检测** | 文档版本号、内容哈希比对、定时重新同步、变更通知 |
| **对话分享与协作** | 会话只读分享链接、知识库团队空间、评论 |
| **管理后台** | 用户 CRUD、用量看板（按用户/按日）、模型使用分布、成本报表 |
| **查询改写** | LLM 生成查询变体并行召回（HyDE / query expansion），提升复杂问题召回 |

### P3｜长期演进的缺口

| 缺口 | 方向 |
| --- | --- |
| **多 Agent 编排** | 当前"最小闭环"的下一步：检索/总结/校对分工，或工具路由 Agent |
| **私有化部署包** | 一键安装脚本、离线模型包、国产化适配（麒麟/统信、达梦/OceanBase） |
| **细粒度权限** | RBAC/ABAC，文档级 ACL，操作审计日志 |

## 三、风险清单

### 技术风险

| 风险 | 等级 | 说明与缓解 |
| --- | --- | --- |
| **onnxruntime 兼容性** | 🔴 高 | Python 3.14 下 DLL 加载失败，本地文档无法入库。缓解：embedding 抽象 + 多后端（见 P0），生产锁定 Python 3.12 容器 |
| **外部模型 API 依赖** | 🟡 中 | DeepSeek/其他 OpenAI 兼容端点超时/限流/下线。缓解：超时降级、多模型配置热切换（已有 model_configs）、健康检查 |
| **单点故障** | 🟡 中 | 单 backend/单 worker/单 DB。缓解：docker-compose 重启策略、worker 多实例（表队列天然支持）、DB 主备（进阶） |
| **流式连接泄漏** | 🟡 中 | 客户端断开后 SSE 连接未释放，耗尽连接池。缓解：`is_disconnected` 检测（已有）、nginx `proxy_read_timeout`、连接数监控 |

### 数据与安全风险

| 风险 | 等级 | 说明与缓解 |
| --- | --- | --- |
| **敏感数据外发** | 🔴 高 | 文档内容经 prompt 发送给外部 LLM API。缓解：数据分级（已有 L1-L4 概念）、L3+ 文档标记"禁止外发"仅本地模型处理、prompt 脱敏钩子 |
| **提示词注入绕过** | 🟡 中 | 当前防护是正则+分隔符，可被精心构造的注入绕过。缓解：定期更新注入样本库、对召回内容做二次指令检测（LLM 自评）、红队测试 |
| **用户隔离失效** | 🟡 中 | 所有查询都靠 `WHERE user_id`，漏一处即越权。缓解：集中查询构造函数强制注入 user_id、定期越权扫描测试 |
| **API Key 泄露** | 🟡 中 | 用户自管 key 加密存 DB（`model_configs`），加密密钥在服务端。缓解：密钥从 KMS/环境变量注入而非硬编码、定期轮换、访问审计 |
| **日志留存合规** | 🟢 低 | 日志含 traceId 与用户行为，需明确留存周期与脱敏规则 |

### 成本风险

| 风险 | 等级 | 说明与缓解 |
| --- | --- | --- |
| **token 费用失控** | 🟡 中 | 恶意/异常刷量导致账单爆炸。缓解：配额硬限（已有原子占用）、单请求 max_tokens 上限、异常用量告警 |
| **配额绕过** | 🟡 中 | 并发/工具回路路径漏算（已修但仍需回归测试）。缓解：配额占用的集成测试、定期对账（DeepSeek 账单 vs 内部累计） |
| **embedding 成本** | 🟢 低 | 本地 BGE 零成本，但若切 OpenAI embedding 则按量计费，需纳入配额 |

### 质量风险

| 风险 | 等级 | 说明与缓解 |
| --- | --- | --- |
| **召回不准（尤其本地 hash 模式）** | 🔴 高 | 若误用 hash fallback embedding，召回无语义等于随机。缓解：禁用 hash 模式进生产、启动时校验 embedding 真实可用、评测基线监控 |
| **幻觉** | 🟡 中 | 模型编造文档中不存在的内容。缓解：prompt 强约束"仅依据资料回答"（已有）、答案与召回块一致性校验、低置信度时拒答 |
| **引用错位** | 🟡 中 | 答案引用角标与实际来源不符。缓解：引用由召回侧确定而非模型输出（已是此设计）、引用块与答案相关性抽查 |
| **切分破坏语义** | 🟡 中 | 表格/代码/跨段引用被切断。缓解：语义分块（按标题层级）、父子块策略（小块召回+大块上下文）、评测驱动调参 |

## 四、文档量增长后的召回精准度保障（专项）

这是当前最薄弱的环节。当文档从几篇增至几百篇、chunk 从几百增至几十万时，单一向量 top_k 的精度会显著下降。分层方案：

### 4.1 索引层：HNSW 参数调优与选型

当前：`CREATE INDEX ix_chunks_embedding ON chunks USING hnsw (embedding vector_cosine_ops)`（默认参数）。

```sql
-- 生产参数（在召回质量与构建/内存成本间权衡）
CREATE INDEX ix_chunks_embedding ON chunks
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- 查询时设置召回质量（越大越准但越慢）
SET hnsw.ef_search = 100;  -- 默认 40，文档量大时提高到 100-200
```

- `m`（每个节点的连接数）：16 是精度/内存平衡点，精度优先可到 32
- `ef_construction`（构建时搜索宽度）：64 足够，100+ 边际收益递减
- `ef_search`（查询时搜索宽度）：这是召回精度的关键，文档量大必须提高，按查询延迟预算调整

**规模阈值参考**：
| chunk 量级 | 建议 |
| --- | --- |
| < 10 万 | HNSW 默认参数 + ef_search=100 足够 |
| 10 万–100 万 | HNSW（m=32, ef_search=200），考虑按 user_id/文档分区 |
| > 100 万 | 评估专用向量库（Qdrant/Milvus/Weaviate），pgvector 单机内存成为瓶颈 |

### 4.2 召回层：混合检索（向量 + 关键词）

单一向量召回对**专有名词、编号、代码、新术语**召回弱（向量不擅长精确匹配）。方案：

```
┌─────────────┐     ┌──────────────────┐
│  用户问题    │────→│ 向量召回 (HNSW)   │──→ top 20
└─────────────┘     └──────────────────┘
        │           ┌──────────────────┐
        └──────────→│ 全文检索 (tsvector)│──→ top 20
                    └──────────────────┘
                            ↓
                    RRF 融合 (Reciprocal Rank Fusion)
                            ↓
                        top 20 混合
                            ↓
                    cross-encoder 重排序
                            ↓
                        top 5 进 prompt
```

PostgreSQL 内即可实现，无需新组件：

```sql
-- chunks 表加全文检索列（迁移）
ALTER TABLE chunks ADD COLUMN content_tsv tsvector
  GENERATED ALWAYS AS (to_tsvector('simple', content)) STORED;
CREATE INDEX ix_chunks_tsv ON chunks USING gin(content_tsv);

-- 关键词召回（BM25 近似用 ts_rank）
SELECT id, ts_rank(content_tsv, plainto_tsquery('simple', :query)) AS rank
FROM chunks
WHERE content_tsv @@ plainto_tsquery('simple', :query)
  AND user_id = :user_id
ORDER BY rank DESC LIMIT 20;
```

**RRF 融合**（Python 端，无需改 DB）：
```python
def rrf_fuse(vector_results, keyword_results, k=60):
    scores = {}
    for rank, item in enumerate(vector_results):
        scores[item.chunk_id] = scores.get(item.chunk_id, 0) + 1 / (k + rank)
    for rank, item in enumerate(keyword_results):
        scores[item.chunk_id] = scores.get(item.chunk_id, 0) + 1 / (k + rank)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)
```

### 4.3 重排序层：cross-encoder rerank

向量/关键词召回是"粗排"（快但不够准），cross-encoder 是"精排"（慢但准，逐对打分）：

```python
# 召回 top 20 → BGE-reranker 重排 → top 5
from fastembed.rerank.cross_encoder import TextCrossEncoder

reranker = TextCrossEncoder(model_name="BAAI/bge-reranker-base")
pairs = [(query, chunk.content) for chunk in top20]
scores = list(reranker.rerank(pairs))  # 逐对计算相关性分数
top5 = sorted(zip(top20, scores), key=lambda x: x[1], reverse=True)[:5]
```

- fastembed 自带 reranker（与 embedding 同框架，无新依赖）
- 本地 CPU 对 20 对重排约 200-500ms，可接受；量大可换 GPU 或更小模型
- **收益最大的一环**：粗排 top 20 里相关块可能排在 8-15 位，重排能提到前 3，直接提升答案质量

### 4.4 切分层：语义分块与父子块

当前按字符窗口切分（512/64），表格、代码、跨段引用易被切断。改进：

1. **语义分块**：按 Markdown 标题层级（# / ## / ###）切段，保持章节完整；PDF 按页+段落边界
2. **父子块策略**：
   - 小块（128-256 字符）用于 embedding 与召回——精度高
   - 大块（父块，含小块上下文）用于注入 prompt——上下文完整
   - 召回小块 → 取父块内容给模型——两全
3. **结构化内容特殊处理**：表格整表为一块（不切行），代码块整段为一块

### 4.5 查询层：查询改写与扩展

复杂/模糊问题直接向量召回效果差。用 LLM 改写：

```
用户问题："报销要多久能批下来？"
  ↓ LLM 查询改写（一次轻量调用）
变体1："差旅报销审批流程与打款时限"
变体2："费控系统报销全流程多少个工作日"
变体3："报销从提交到打款需要几天"
  ↓ 三个查询并行召回（向量+关键词）
  ↓ RRF 融合 → 重排 → top 5
```

成本：每次问答多一次轻量 LLM 调用（可用便宜模型）+ 3 倍召回计算。收益：复杂问题召回命中率显著提升。

### 4.6 监控层：召回质量基线

精准度不能只靠"感觉"，必须有持续监控：

| 指标 | 方法 | 告警阈值 |
| --- | --- | --- |
| 召回命中率 | 评测集（30 问）定期跑，gold_doc 在 top5 比例 | 周环比下降 > 5% |
| 重排提升率 | 重排前后 gold_doc 排名对比 | 基线存档 |
| 零召回率 | 召回结果为空或最高分 < 阈值的比例 | > 10% |
| 坏答案反馈率 | 用户点踩 / 总回答数 | > 5% |
| 引用点击率 | 引用面板打开 / 总回答数 | 持续下降 |

### 4.7 精准度演进路线（按投入产出比排序）

```
阶段1（1-2 天，收益最大）
  └─ HNSW 参数调优 + ef_search 提高 + 重排序接入
     → 召回精度预计 +20-30%，无需新组件

阶段2（2-3 天）
  └─ 混合检索（tsvector + RRF）
     → 专有名词/编号类问题召回显著改善

阶段3（3-5 天）
  └─ 语义分块 + 父子块
     → 长文档/结构化文档答案质量提升

阶段4（按需）
  └─ 查询改写 + 监控告警
     → 复杂问题覆盖 + 质量可持续

阶段5（文档 > 50 万 chunk）
  └─ 专用向量库（Qdrant）+ 分区 + GPU reranker
     → 支撑大规模，pgvector 平滑迁移
```

## 六、关键决策原则

1. **精准度优先于功能广度**：先把召回做准（阶段1-3 是投入产出比最高的），再扩功能。召回不准，功能再多也没人用。
2. **无新组件优先**：混合检索、重排、RRF 都能在现有 Postgres + fastembed 内实现，不引入新中间件，降低运维成本。只有到阶段5（50 万 chunk+）才引入专用向量库。
3. **生产/开发分离**：embedding 抽象化后，开发环境可用轻量后端，生产锁 Docker+Python 3.12+真实 BGE，杜绝 hash 模式进生产。
4. **安全是底线不是功能**：敏感数据外发控制、注入防护、用户隔离是 P0 级，必须在扩功能前加固。
5. **一切用评测说话**：召回改动必须跑评测集对比前后指标，无指标不合并。评测集随文档增长持续扩充（30 → 100+）。
